At the user's request, existing responses and collected attack-history assets
were backed up and replaced with a fresh Terra baseline. No raw commands,
credentials, endpoints, or personal telemetry are reproduced in this artifact.

## Backup and generation

Writers were stopped before the backup. The private ignored directory
`backups/terra-rebuild-20261029/` contains about 4.5 GB: the entire runtime
publication worktree including its Git database, raw session files, runtime logs,
the old cache, and the separate host publication checkout. SHA-256 checksums of
the cache/history and generation-work archives are recorded in its private
manifest. The backup contains sensitive harvested data and must not be published.

The single-container supervisor gained maintenance mode: it runs only the bridge,
without the SSH application. All generation used `openai/gpt-6.1-terra` through
the protected in-container bridge, never a tool-capable agent or real shell.
Existing cache keys supplied coverage; old response values were not reused.
Canonical placeholders were materialized using synthetic values, then re-templated.

Result: 272 regenerated cache entries and 10 new model-designed synthetic
playbooks with 47 stateful command/response turns. Generated baseline responses
use `origin=seed` with genuine Terra model attribution and timestamps, enabling
the existing reviewed-baseline compound-cache path. Later runtime learning uses
`origin=llm`. Scenario documents are explicitly synthetic and remain separate
from collected attacker events. The output assets and provenance/completion
manifests reside under `FunnyPot/data/`.

Generation is resumable against an unchanged source SHA-256, limited to two
concurrent calls, and retries invalid output. Core persona/compound-output
checks are enforced. Validation exposed and repaired CPU-fallback diagnostic
drift, binary-output truncation handling, and LF/CRLF differences for the
authoritative synthetic OS-release file. Rejected answers were regenerated by
Terra, not copied from older assets. This is automated validation, not a claim
of exhaustive semantic correctness of every model output.

## Attack-history reset

**Later publication incident:** the initial post-reset container was healthy,
but its supervised app inherited HOME=/root and failed to publish newly collected
events. Those records stayed local and were fully recovered after correcting
the user environment. See `publication-home-environment-incident-2026-10-29.md`;
the verification below describes initial reset/local collection, not proof that
ongoing publication was working at that earlier point.

After backup, current runtime events, summaries, threat intelligence, structured
debriefs, raw session files, and global statistics were reset. The new empty
baseline was committed/pushed on the publication data branch as `6d996207`
(`Reset backed-up attack history for Terra 6.1 baseline`), using a normal
fast-forward push. Remote history was not rewritten; prior records remain in
historical commits and the local backup. The separate host frontend checkout
was backed up but is not the active runtime publication store.

Synthetic model-generation activity did not create real attacker event records.
New real activity will naturally populate the clean baseline. Generation staging,
including original input and all checkpoints, was archived into the private
backup and removed from the active data directory.

The populated baseline passed all 136 .NET tests, including existing cache/persona
contracts; the Python bridge suite contains 17 tests. Deployment documentation
describes maintenance, generation, validation, activation, reset, and recovery.

Final deployment verification: maintenance mode was removed, the image rebuilt
with the new assets, and the single container recreated and healthy on port
22722. A direct app-user model check returned `Linux` without producing attacker
telemetry. Runtime audit confirmed 272 cache entries all attributed to Terra,
10 synthetic scenarios / 47 turns, and no staging directory. Immediately after
restart the active publication store had zero event bytes, zero sessions,
zero total events, and zero harvested usernames. All 136 .NET and 17 Python
tests passed. This data-branch reset does not imply a commit/push of parent
repository source/cache changes; those remained pending at task completion.
